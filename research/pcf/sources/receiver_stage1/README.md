# PCF receiver security baseline — stage 1

This is a separate receiver application for the existing BRAM protected-chunk
hardware. It does not change RTL, claim hardware-enforced authorization, or
replace your original project. Use the fresh baseline XSA:

C:/PCF/bram_baseline_20261018_200837/scripts/zcu104_gcm_protected_chunk.xsa

## 1. Extract and run offline fixtures

Extract this ZIP to C:/PCF/receiver_stage1 (the ZIP contains the files directly).
In PowerShell:

```powershell
cd C:\PCF\receiver_stage1
py -m pip install -r host\requirements.txt
py host\test_external_receiver.py --self-test
```

Expected: `OFFLINE FIXTURES PASS: 11 cases; FPGA not tested.`

## 2. Build a separate Vitis application

Use Vitis Embedded 2026.1 and a separate workspace, for example
C:/PCF/vitis_receiver_stage1. Create a platform using the XSA above, selecting
psu_cortexa53_0 and standalone. Build the platform, then create an empty application
using that domain. Add software/main_gcm_receiver.c and software/platform.h.
Ensure there is exactly one main function; remove an autogenerated application
main if present. Do not add the old main_gcm_dma_protected_chunk.c to this app.
Build and inspect all errors. The source uses the same AXI addresses and DMA
API as your uploaded working application.

This package was not compiled with the actual AMD BSP here. Both SDT and non-SDT
branches passed host C syntax checking using mocked BSP declarations; a real
Vitis compile/link remains required.

## 3. Physical-board suite

Close other serial terminals. Identify the actual UART COM port in Windows;
COM11 is only an example. Connect and power ZCU104. In PowerShell, start:

```powershell
cd C:\PCF\receiver_stage1
py host\test_external_receiver.py --port COM11
```

When the host prints `Port open`, program the matching fresh-baseline hardware
and reset/launch the NEW receiver application in Vitis. The host waits up to
120 seconds for its startup banner. It must be launched after the host is
listening. Relaunch/reset the app before each new suite to clear volatile
freshness state; the test begins at sequence 100 on each run.

Expected: 11 individual PASS lines and `BOARD OVERALL: PASS`.
A timestamped receiver_run_* folder contains summary.json and uart_transcript.txt.
Return both files and the Vitis build log for review. A failure records partial
evidence with overall_pass false. Do not describe offline PASS as a board PASS.

## Suite

Synthetic 17x19 RGB888 data (969 bytes) avoids patient data and image path setup.
Tests: valid input; ciphertext first/middle/last-byte changes; altered tag;
altered IV; changed structurally valid metadata; ciphertext made with a wrong
key; malformed declared length; replay of an accepted frame; valid input after
rejections. The receiver always uses the fixed public demonstration key.
Dimensions can be changed with --width and --height but must be unequal and
fit in one 4096-byte chunk. This first suite does not test multi-chunk assembly.

## Receiver framing

32-byte header: `RCV3` + 16-byte CHK3-compatible AAD + 12-byte IV. Version remains
3 because the cryptographic AAD encoding is unchanged. RCV3 is a distinct
transport magic so the original plaintext-input host cannot silently use it.
After RX_READY_CIPHERTEXT, send ciphertext followed by the 16-byte expected tag.
Malformed/replayed headers get rejected BEFORE their bodies are sent.
`END3` followed by 28 zero bytes ends a session.

The firmware never encrypts received input in this mode. It authenticates the
received ciphertext against the received tag, keeps S2MM unarmed during auth,
checks the untouched output sentinel, and decrypts the same locked copy only
on a successful check. It verifies second-pass status before UART transmission.
Normal rejection scrubs the on-chip buffer and clears DDR transaction buffers.
Freshness state is committed only after successful authentication/release.

## What this establishes and what it does not

This is a trusted-firmware baseline for externally supplied ciphertext. UART
plaintext absence and firmware-reported probes are checked. It is not an
independent monitor of every DDR write or internal AXI output. A later RTL
interlock and assertions/bus monitoring are needed for stronger release claims.
Keys/configuration remain software controlled; replay state is volatile and
resets when the application restarts. The public key is for demonstration only.
The UART recovered output is intentionally plaintext for verification.

The blocking receive_exact routine is inherited from the working firmware.
A truncated body can block until application reset; transport timeout/abort
hardening is a later task. Internal hardware/driver failures halt the app and
require reset/relaunch; these paths do not claim complete on-chip cleanup.
